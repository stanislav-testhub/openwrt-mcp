[MCP](https://modelcontextprotocol.io)-сервер, который работает **на** роутере с OpenWrt, чтобы
Claude Code (или любой MCP-клиент) мог его просматривать и менять -- под защитой политик
«запрещено по умолчанию», журнала аудита и автоматического отката изменений конфигурации.

**Локально и приватно.** Сервер сам не устанавливает исходящих соединений и не отправляет
телеметрию; он слушает loopback и сокет, доступный только root, и общается с вашим клиентом через
SSH-сессию, которую вы настраиваете сами. Инструменты, из-за которых сам роутер может выйти в сеть
(`net_diag`, `pkg_query` с `refresh`, `pkg_change`, `sysupgrade check`, проверки `uci_apply`
(probes), `ubus_call`, `exec`), сообщают об этом в MCP-аннотациях (`openWorldHint`), и для каждого
нужно ваше разрешение. Секретные значения в выводе инструментов по умолчанию маскируются, а новый
ключ WireGuard не попадает в диалог, пока вы сами этого не попросите.

**Размер.** Один статический бинарник без зависимостей: от 9,1 до 11,3 МБ для архитектур роутеров
(9,6 МБ на arm64, около 3,7 МБ в сжатом архиве релиза), около 10 МБ в памяти на GL-MT6000
сразу после запуска, и 23 инструмента в примерно 22 КБ описаний. Каждый файл релиза снабжён
контрольной суммой и аттестацией сборки.

> **Основано на [GlassOnTin/openwrt-mcp](https://github.com/GlassOnTin/openwrt-mcp)** Йена
> Уильямса (Ian Williams); тот проект рассчитан на прошивку GL.iNet 4.x (OpenWrt 21.02, `opkg`).
> Это порт на **стоковый OpenWrt 25.12** (`apk`, fw4/nftables, procd, netifd, LuCI JS). Ядро
> безопасности взято из оригинала; что откуда пришло, см. в разделе [Благодарности](#благодарности).

## Требования

- **Роутер:** стоковый OpenWrt **25.12** (`apk`) или **24.10** (`opkg`), оба с fw4/nftables. Заранее ничего
  устанавливать на роутер не нужно. Менеджер пакетов выбирается по двоичным файлам на роутере (сначала `apk`,
  затем `opkg`); `system_status` сообщает, какой из них и какой межсетевой экран найден.
  - **Что отличается на 24.10:** у `pkg_query` нет `policy` и `audit` (в opkg их нет; инструмент об этом говорит).
    `pkg_change` симулирует через `opkg --noaction`. Новые значения пакетов приходят как `<file>-opkg` вместо
    `<file>.apk-new`; `pkg_config_diff` / `pkg_config_resolve` понимают оба варианта (старая копия сохраняется как
    `.pre-opkg-new`). `world` перечисляет пакеты, которые opkg считает «установленными пользователем».
    `system_status mode=doctor` сообщает `opkg-new-pending`; `mode=audit` пропускает аудит пакетов и объясняет почему.
  - **fw3 (OpenWrt 21.02 и старше или прошивки на его основе):** по мере возможности. `firewall_show` отвечает на
    `ruleset` (`iptables-save`, IPv4) и `rendered` (`fw3 -q print`); `check`, `table` и `chain` отклоняются; применение
    правил межсетевого экрана заранее не проверяется.
  - **Проверено на:** 25.12.5 на GL-MT6000 (железо); модульные тесты прогоняют оба менеджера на подделках; CI запускает
    инструменты пакетов и uci в контейнерах `openwrt/rootfs` 24.10 и 25.12 (ubus и netifd там нет, поэтому пути сети,
    Wi-Fi и межсетевого экрана не покрыты). Прошивки на основе OpenWrt (GL.iNet, ImmortalWrt) -- по мере возможности.
- **Ваш ПК:** OpenSSH (есть в Windows 10 и новее, macOS и Linux). Для установки из релиза больше
  ничего не нужно. Для сборки из исходников нужны Go 1.26+, `ssh` и `tar` (Linux, macOS или
  Git Bash в Windows).
- **Любой процессор, который поддерживают и OpenWrt, и Go:** в релизе есть бинарник для каждого
  (arm64, armv5/v7, mips/mipsle softfloat, mips64/mips64le, x86, x86-64, riscv64); `install.sh`
  читает `DISTRIB_ARCH` роутера и выбирает нужный, а при сборке из исходников кросс-компилирует.

Проверено на GL.iNet GL-MT6000 (mediatek/filogic, `aarch64_cortex-a53`) с OpenWrt 25.12.5.
В коде нет ничего, что было бы привязано к этой плате.

## Инструменты

| Инструмент | Область | |
|---|---|---|
| `system_status` | инструмент | Модель, релиз, аптайм, нагрузка, память, хранилище, температуры, conntrack, все интерфейсы (состояние, адреса, маршрут по умолчанию, ошибки), радиомодули/SSID и то, что требует внимания. Вызывайте первым. `mode=doctor` возвращает ранжированные находки о состоянии (радио выключено, интерфейс без адреса, включённая служба упала, conntrack и хранилище почти заполнены, ожидающие `.apk-new`, NTP или не заданные часы, установлено более новое ядро, чем запущено). `mode=audit` возвращает ранжированные находки по безопасности (что файрвол пускает из интернета, доступность SSH и LuCI, вход по паролю, UPnP, WPS, открытый или слабый Wi-Fi, пустой пароль root, изменённые файлы пакетов, устаревшие пиры WireGuard). Оба режима носят рекомендательный характер: каждая находка называет следующий вызов только для чтения и страницу вики OpenWrt, а также перечисляет то, что проверить не удалось. Это отдельные области: `openwrt-mcp allow <client> system_status doctor`. |
| `logread` | инструмент | Весь буфер журнала фильтруется (подстрока, RE2, последние N минут) *до* ограничения числа строк; `offset` листает назад от самой новой строки. `mode=summary` сворачивает его до различных сообщений (числа, адреса и идентификаторы становятся заполнителями) со счётчиком, временем первого и последнего появления и наивысшей серьёзностью. `baseline=save` возвращает токен; `baseline=<token>` показывает только те сообщения, которых тогда в журнале не было. Базовые линии хранят отпечатки, а не текст журнала, и живут в памяти. |
| `network_clients` | инструмент | Аренды DHCP + статические хосты + таблица соседей + список ассоциаций каждой точки доступа, объединённые по MAC: имя, IP, SSID, уровень сигнала, скорости, время подключения, доля эфирного времени радиомодуля у каждого клиента (по данным hostapd), аренда; 100 строк на страницу, `offset` для следующей. |
| `firewall_show` | инструмент | `nft list ruleset`, `fw4 print`, `fw4 check`, одна таблица или цепочка. |
| `net_diag` | `<action>[.<target>]` | ping / traceroute / nslookup (при желании с указанного интерфейса), маршруты, правила политик, соседи. `wifi_survey` сообщает по каждому радиомодулю, насколько занят канал, на котором он работает (занятость, эфирное время rx и tx, шум); остальные каналы не измеряются, поэтому канал он никогда не рекомендует. `traffic` несколько секунд замеряет скорости интерфейсов и ранжирует таблицу conntrack по источнику. `usage` читает итоги nlbwmon по устройствам за расчётный период (по умолчанию месяц). Все три только читают. |
| `uci_get` | `<config>[.<section>[.<option>]]`; `refs` для поиска имени | `uci show`, при желании со стабильными идентификаторами `cfgXXXXXX`. Заканчивается **ревизией** конфигурации. `history=list` / `diff:<id>` показывает сохранённые версии, бывшие до каждого подтверждённого изменения. `refs=NAME` находит, что определяет и использует имя во всех конфигурациях. |
| `uci_apply` | `<config>.<section>[.<option>]` на изменение; `<config>` для `restore`; `probe.<kind>.<target>` на проверку | Подготовить, проверить, зафиксировать, перезагрузить, **откат взведён**. `dry_run` показывает, что именно изменится и что говорит собственный проверяющий механизм службы. `expected_revisions` отказывает, если за это время конфигурация изменилась, `probe` проверяет роутер после изменения, `restore=<id>` возвращает прошлую версию. После фиксации конфигурация читается обратно; изменение, которое роутер не сохранил, получает статус `NOT_APPLIED`, и ничего не перезагружается. |

| `mfa_unlock` | *(без ограничений)* | Открывает окно TOTP для инструментов, защищённых MFA. |

**Подсказки (prompts).** Клиенты, которые показывают MCP-подсказки (обычно как слэш-команды),
получают пять рецептов: `router-health`, `who-is-online`, `secure-my-router`, `wifi-doctor` и
`upgrade-plan`. Каждый -- это несколько строк с названиями инструментов для вызова, которые
заканчиваются отчётом или предложением, но никогда не изменением. Они используют только то, что
даёт пресет `@readonly`, поэтому клиент только для чтения может пройти их до конца, и до
использования они ничего не стоят. Просмотр или получение подсказки ничего не запускает на
роутере, поэтому политики не применяются и аудит не ведётся.

### Предупреждения, ссылки, пиры и дополнения

**Предупреждения при пробном запуске.** `uci_apply dry_run` заканчивается блоком `warnings from this change`: находки, которые
изменение добавило бы по сравнению с текущим состоянием роутера, ранжированные как в аудите, каждая со следующим шагом и страницей
вики OpenWrt. Это совет, а не отказ. Они охватывают порт или проброс порта, открытый в интернет, `ACCEPT` на входе или пересылке
зоны WAN, включённый вход по паролю в SSH, SSID без шифрования, имя, которое изменение удаляет или пишет с ошибкой, пока другие
секции его ещё используют (`ref-removed`, `ref-unknown`, с подсказкой «возможно, вы имели в виду» при расхождении регистра), и
изменение, отключающее Wi-Fi сеть, через которую подключён ваш собственный сеанс (`radio-in-use`). То, что было неверно ещё до
изменения, повторно не сообщается. Настоящее применение их не повторяет, поэтому сначала запускайте пробный запуск.

**Путь управления следует за вашим сеансом.** Помимо LAN, его моста, SSH-слушателя и зоны с правилом для SSH, путём управления
считается интерфейс, через который приходит ваше SSH-подключение (демон определяет адрес клиента через `ip route get`), поэтому
изменения туннеля WireGuard, по которому вы подключены, требуют проверки (`probe`) или `force=true`, как и изменения LAN.

**Прежде чем переименовать или удалить интерфейс, зону или устройство.** `uci_get refs=lan` перечисляет, что определяет это имя
(сетевой интерфейс, зону межсетевого экрана, устройство, радиомодуль, участника или политику mwan3), и каждое поле-ссылку, которое
его использует: `network` зоны, `src` и `dest` правила/перенаправления, `interface` в dhcp, `network` и `device` в wireless,
`device` и `ports` в network, `route.interface`, `sqm` и `mwan3`, если установлены. «defined as: nothing» означает, что секции
с таким именем нет (опечатка или расхождение регистра). Читаются только эти поля, поэтому поиск нельзя использовать для
выяснения ключа. Нужна область `refs`, которую включают `@readonly` и `@operator`; `config=firewall` сужает поиск до одной
конфигурации.

**Добавление и удаление пиров WireGuard -- обычное изменение со взведённым откатом.** Пир записывается в `/etc/config/network`,
и netifd загружает его, поэтому сеансы других пиров не рвутся. Оба инструмента ждут, пока пир появится на работающем интерфейсе
(или исчезнет с него), и сообщают, что проверили. До `uci_confirm` ничего не окончательно: иначе по таймауту или после
перезапуска пир убирается обратно, а файл ключа нового клиента удаляется. Одновременно подтверждения может ждать только одно
изменение. Удаление пира, через которого приходит ваш собственный сеанс, требует `force=true`.

**Состояние дополнений.** `service_list detail=NAME` читает установленное дополнение (его init-скрипт существует) и печатает
фиксированный набор полей только для чтения: он никогда не повторяет файл конфигурации или сырой вывод команды, потому что в них
бывают хэши входа, ссылки прокси, ключи узлов и токены. Для выдачи нужна область службы (`tailscale.detail` или `*`, как в
`@readonly`); обычный список ничего не требует. Текст, который выбрал кто-то другой, например имя хоста пира tailnet, обрезается,
очищается и помечается как недоверенный.

| Дополнение | Что сообщает | Проверено |
|---|---|---|
| tailscale | состояние, DNS-суффикс tailnet, адреса этого узла, анонсируемые маршруты, выходной узел, здоровье, пиры (в сети, напрямую или через ретранслятор, трафик) | GL-MT6000, 25.12 |
| AdGuard Home | работает ли, адреса прослушивания, переключатели защиты и фильтрации, upstream-серверы (только схема и хост), bootstrap, число списков фильтров и правил, перенаправляет ли на него dnsmasq | GL-MT6000, 25.12 |
| podkop | версия, работает ли sing-box, таблица nft, путь dnsmasq, настройки, по строке на секцию (тип, интерфейс, списки сообщества, размер динамических списков) | GL-MT6000, 25.12 |

Намеренно не читаются: веб-API AdGuard Home (нужен вход в интерфейс), `proxy_string`, селекторы и настройки исходящих у podkop,
а также списки доменов и подсетей пользователя.

## Установка

**На роутере, из релиза** (достаточно стандартного образа 25.12):

```sh
wget -O /tmp/install-router.sh https://github.com/stanislav-testhub/openwrt-mcp/releases/latest/download/install-router.sh
sh /tmp/install-router.sh
```

Скрипт выбирает архив под `DISTRIB_ARCH` роутера, сверяет его с `SHA256SUMS` релиза (при
несовпадении отказывается) и устанавливает. `VERSION=v1.2.0` выбирает релиз, отличный от
последнего. Каждый файл релиза также снабжён аттестацией сборки:
`gh attestation verify <file> --repo stanislav-testhub/openwrt-mcp`.

**С ПК, сборка из исходников** (нужны Go, ssh и tar; в Windows подойдёт Git Bash):

```sh
git clone https://github.com/stanislav-testhub/openwrt-mcp
cd openwrt-mcp
ROUTER=root@192.168.1.1 SSH_PORT=22 SSH_KEY=~/.ssh/id_ed25519 ./install.sh install
```

`ROUTER`, `SSH_PORT` и `SSH_KEY` -- это вход root на вашем роутере (по умолчанию:
`root@192.168.1.1`, 22, ваши настройки ssh). `./install.sh install --release [vX.Y.Z]`
пропускает сборку и просит роутер скачать проверенный релиз; то же происходит, если Go не найден.

В обоих случаях на роутере запускается один и тот же установщик.
- Он устанавливает:
  - `/usr/bin/openwrt-mcp`;
  - скрипт инициализации;
  - конфигурацию по умолчанию, никогда не перезаписывая существующую;
  - запись `keep.d`;
  - страницу LuCI.
- Затем он включает и запускает службу.
- Он отказывается перезапускать демон, пока `uci_apply` ждёт подтверждения, потому что это
  привело бы к откату, если не задано `FORCE=1`.
- Сначала он проверяет, что бинарник помещается в overlay.

`./install.sh uninstall [--purge]` всё это отменяет.

### Страница состояния в LuCI

После установки *Services -> MCP Server* в LuCI показывает демон (работает или остановлен, версия,
HTTP-слушатель, сокет stdio), ожидающий `uci_apply` с крайним сроком автоматического отката,
спаренных HTTP-клиентов, действующие политики и последние записи аудита. Страница только для
чтения намеренно: спаривание и разрешения остаются в командной строке, поэтому ничто, доступное
по сети, не может расширить права агента.

**Почему не `.apk`:** пакеты 25.12 -- это архивы ADB формата apk-tools v3. Чтобы собрать такой,
нужен OpenWrt SDK или хостовый apk-tools с `mkpkg` (в apk на роутере `mkpkg` нет), а
неподписанный пакет всё равно требует `--allow-untrusted`. Статический бинарник ничего не теряет
от установки файлами: `/etc/config` переживает sysupgrade сам по себе, а
`/lib/upgrade/keep.d/openwrt-mcp` сохраняет бинарник, скрипт инициализации, ссылки rc.d, состояние
и страницу LuCI. (Образ `owut`/ASU пересобирает *пакеты*, а не отдельные файлы -- сохраняет это
при обновлении именно запись keep.d.)

## Подключение

### `openwrt-mcp connect` (рекомендуется)

В релизе есть бинарник и для вашего ПК (`openwrt-mcp_<version>_windows_amd64.zip`,
`darwin_arm64.tar.gz` и так далее; на Linux-ПК подойдёт архив `linux_`). Распакуйте его в любое
место из `PATH`; ему нужен OpenSSH, который есть в Windows 10 и новее, macOS и Linux. Затем на ПК:

```sh
openwrt-mcp connect --client claude-code --host 192.168.1.1          # or claude-desktop, codex, cursor, gemini, vscode
```

Команда создаёт отдельный ключ ed25519 (`~/.ssh/openwrt_mcp`, существующий никогда не
перезаписывается), печатает две команды, которые нужно один раз выполнить на роутере, и показывает
запись, которую нужно добавить в клиент. С `--write` она выполняет и этот последний шаг: для
Claude Code и Codex запускает их собственный `mcp add`, для Claude Desktop, Cursor, Gemini CLI и
VS Code вливает одну запись `openwrt` в их JSON-файл (остальные серверы остаются; оригинал один
раз сохраняется как `<file>.before-openwrt-mcp`; файл с комментариями не трогается, а вместо этого
печатается фрагмент). В записи `ssh` и его аргументы хранятся списком, поэтому пробелы в пути к
ключу не требуют экранирования, и задаются keep-alive, чтобы перезагрузку роутера было заметно.

```sh
openwrt-mcp connect doctor --host 192.168.1.1
```

проверяет цепочку по порядку и останавливается на первом разрыве, предлагая одно исправление:

```
[ ok ] ssh reachable   192.168.1.1:22
[ ok ] host key
[ ok ] key accepted    /home/you/.ssh/openwrt_mcp
[FAIL] forced command  the key logged in, but nothing answered as an MCP server (...)
       fix: the key is probably authorized without its forced command ...
[skip] daemon socket
```

Шаги: SSH доступен, ключ хоста, ключ принят, принудительная команда, сокет демона, `initialize`,
`tools/list`. Неверный ключ, отсутствующая принудительная команда, остановленный демон и
отключённый сокет называют каждый свой шаг.

**После перезагрузки или перезапуска демона.** Перезагрузка, обновление через `install.sh` или сбой завершают все открытые
сеансы: мост `openwrt-mcp stdio` выходит с `daemon closed the connection`, и клиент показывает сервер как отключённый.
Не все MCP-клиенты переподключаются сами, поэтому переподключитесь из клиента (его меню MCP или перезапуск клиента). После
загрузки SSH отвечает на несколько секунд раньше, чем демон начинает слушать; мост ждёт сокет демона до 10 секунд, прежде чем
завершиться с `daemon not reachable ... after waiting 10s` (и `[code: TIMEOUT; ...]`), поэтому переподключение сразу после
возвращения роутера обычно просто работает, а если нет -- подождите несколько секунд и переподключитесь снова. Изменение, всё ещё
ждавшее `uci_confirm`, откатывается при следующем запуске. `openwrt-mcp status` показывает последнее отключение и его причину
(`client closed the connection`, `connection error: ...` или `the daemon restarted (router reboot, upgrade or crash)`), которую
берёт из журнала аудита; там же по одной строке `stdio session closed after ...` на сеанс и `daemon started` на запуск.

### Более узкие сеансы и командная оболочка

**Попросите меньше, чем разрешает ключ.** Политика решает, что клиенту можно; клиент может также попросить *меньше* на один сеанс.

```sh
openwrt-mcp connect --client claude-code --host 192.168.1.1 --read-only            # ничего, что меняет роутер
openwrt-mcp connect --client claude-code --host 192.168.1.1 --toolset diag,pkg      # только эти инструменты
```

Наборы: `diag` (`logread`, `network_clients`, `firewall_show`, `net_diag`, `service_list`, `ubus_list`, `ubus_call`),
`config` (`uci_get`, `uci_apply`, `uci_confirm`, `uci_rollback`, `service_control`), `pkg` (`pkg_query`, `pkg_change`,
`pkg_config_diff`, `pkg_config_resolve`, `sysupgrade`) и `wg` (три инструмента WireGuard). `system_status` есть всегда;
`exec` не входит ни в один набор. `--read-only` -- это пресет `@readonly`, пересечённый с разрешениями клиента, поэтому он
может только убирать права, а скрытый инструмент отклоняется при вызове, а не просто пропадает из списка. Профиль передаётся
словами после принудительной команды (`SSH_ORIGINAL_COMMAND`), которые демон разбирает по фиксированной грамматике: всё
остальное отклоняется и записывается в аудит, и в ней нет слова, расширяющего сеанс.

**Из оболочки или скрипта, без MCP-клиента.** Тот же SSH-ключ запускает по одному инструменту:

```sh
ssh -T root@192.168.1.1 call --list
ssh -T root@192.168.1.1 call uci_get --help
ssh -T root@192.168.1.1 call uci_get '{"config":"network"}'
ssh -T root@192.168.1.1 -- --read-only call uci_get '{"config":"network"}'   # после слова профиля `--` завершает собственные параметры ssh
```

Результат -- текст в stdout; отказ или ошибка идут в stderr со строкой `allow` и кодом выхода 1. Вызов проходит через те же
политику, аудит и маскирование, что и сеанс MCP. `skills/openwrt-mcp/SKILL.md` -- готовый файл навыка для агентов, которым
оболочка удобнее MCP.

**Ограничения.** У каждого инструмента есть срок выше его собственных ожиданий, и одновременно выполняется не более 8 вызовов:
остальные ждут до 30 с и затем получают отказ `busy` (`TIMEOUT`). Клиент, отменивший вызов, убивает запущенную им команду.
`uci_confirm`, `uci_rollback` и `mfa_unlock` никогда не ждут свободного места.

### stdio поверх SSH, вручную

Отдельный ключ, привязанный на роутере к MCP-мосту и ни к чему больше:

```sh
ssh-keygen -t ed25519 -N '' -f ~/.ssh/openwrt_mcp
ssh root@router "openwrt-mcp authorize-key claude-code '$(cat ~/.ssh/openwrt_mcp.pub)'"
ssh root@router "openwrt-mcp allow claude-code @readonly 30d"
claude mcp add openwrt -- ssh -T -i ~/.ssh/openwrt_mcp -o BatchMode=yes root@router
```

`authorize-key` записывает строку вида
`command="/usr/bin/openwrt-mcp stdio --client claude-code",no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty ssh-ed25519 ...`
в `/etc/dropbear/authorized_keys`: этот ключ получает MCP-сервер под именем клиента
`claude-code` и не может ни открыть оболочку, ни пробросить порты. Ключ, который уже является
входом root, он отвергает.

Мост передаёт сессию в unix-сокет, доступный только root (`/var/run/openwrt-mcp/mcp.sock`,
0600 в каталоге 0700). Инструменты выполняет **демон**, поэтому откат, взведённый в одной
сессии, переживает её. Имя клиента на сокете заявляется, а не доказывается -- это допустимо,
потому что подключиться может только root, а root и так может править файл политик; настоящая
аутентификация -- это ключ SSH.

В Windows для этого подходит встроенный клиент OpenSSH (`ssh.exe`); указывайте полный путь к ключу.

### HTTP через туннель

Без изменений по сравнению с оригиналом: `openwrt-mcp pair <client>` один раз печатает bearer-токен;
`ssh -N -L 8730:127.0.0.1:8730 root@router`; затем
`claude mcp add --transport http openwrt http://127.0.0.1:8730/mcp --header "Authorization: Bearer $TOK"`.
Демон отказывается привязываться к чему-либо, кроме loopback.

### Чтобы политика что-то значила

Если агент может запустить `ssh root@router ...` через свой инструмент оболочки, политика носит
лишь рекомендательный характер. Запретите это в клиенте (Claude Code: правило
`permissions.deny` для `Bash(ssh * root@<router>*)`) или храните ключ root там, где агент не
может его прочитать.

## Политики

Запрещено по умолчанию. Политика даёт одному клиенту список инструментов, маски областей (`*` и
`?` -- подстановочные знаки; скобки буквальные), потолок вызовов в минуту и срок действия.
Изменения в `/etc/config/openwrt-mcp` вступают в силу без перезапуска.

```sh
openwrt-mcp allow claude-code @readonly 30d          # every read tool; ubus_call on an allow-list of read methods
openwrt-mcp allow claude-code @operator 7d           # + uci_apply/confirm/rollback, service_control, pkg_change,
                                                      #   pkg_config_resolve, wg_new/remove_client, sysupgrade backup
openwrt-mcp allow claude-code uci_apply 'dhcp.* wireless.*.disabled' 30d
openwrt-mcp allow claude-code service_control 'dnsmasq.restart adguardhome.*' 30d
openwrt-mcp revoke claude-code                        # remove every policy for the client
openwrt-mcp prune --older-than 7d                     # delete grants that expired over a week ago (audited)
openwrt-mcp policies | status [--all] | clients
```

Повторная выдача тех же инструментов и областей заменяет истёкшее разрешение клиента, а не
добавляет новый блок. `status` в одной строке считает истёкшие разрешения; `--all` перечисляет их.

Ни один пресет не включает `exec` и неограниченный `ubus_call`: оба обходят защитные механизмы.
Список ubus только для чтения состоит из явных пар `object.method`, а не масок вида `*.list`,
потому что `session.list` возвращает идентификаторы сессий LuCI. `uci_get '*'` читает все
конфигурации, но значения секретных опций (ключи Wi-Fi, ключи WireGuard, пароли, токены)
возвращаются как `<redacted>`; см. *Модель безопасности*. `exec` не маскируется.

Отказ называет непокрытую область и печатает точную строку `allow`, которая бы её покрыла.

Область `exec` -- это буквально `argv[0]`, поэтому разрешение на `find` или `awk` выглядит
безобидно, но это оболочка root: оба запускают другие программы, как и оболочки, `env`, `nice`,
`flock`, `timeout`, `xargs`, `tar`, `ssh`, `lua`, `ucode`, `apk` и `opkg`. `allow` отказывает в
таком разрешении, пока вы не добавите `--shell-equivalent`, определяя по базовому имени, поэтому
`/usr/bin/../bin/sh` и `/bin/*` тоже считаются; разрешение на `ubus_call`, способное дотянуться
до `file.exec`, трактуется так же. `openwrt-mcp policies` и `status` помечают такие разрешения, что
покрывает и вручную написанную политику. Этот список -- нижняя планка, а не гарантия: разрешение,
позволяющее записывать файлы (`wget`, `cp`, `dd`) или запускать интерпретатор, которого в списке
нет, всё равно можно использовать во зло.

### Второй фактор

Без изменений по сравнению с оригиналом: `openwrt-mcp mfa enrol <client>` печатает URI
`otpauth://`; затем в политике `list mfa_tools 'uci_apply'`, `option mfa_window '15m'`. Один код
открывает окно ограниченной длительности; коды одноразовые; разблокировки хранятся только в памяти.

Неверные коды ограничены: в секции `config server` `option mfa_max_failures '5'` подряд идущих
неверных кодов блокируют этого клиента в `mfa_unlock` на `option mfa_lockout '300'` секунд (`'5m'`
тоже работает), удваивая срок при каждом повторе, до одного часа. Верный код во время блокировки
отклоняется и не расходуется. Клиент без секрета считается так же, поэтому лимит ничего не
выдаёт о том, зарегистрирован ли клиент, а счётчики хранятся в памяти (перезапуск, `mfa enrol` или
смена секрета их сбрасывает). Каждый неверный код записывается в аудит как `ERROR`, блокировка --
как `DENIED`; сам код не логируется никогда. Цена: тот, у кого есть токен клиента, может держать
этого клиента заблокированным до часа.

## Модель безопасности

- **Откат, переживающий самое вероятное событие.** `uci_apply` сохраняет снимок затронутых
  конфигураций в `/etc/openwrt-mcp/rollback/<token>/` (с fsync), записывает ожидающую запись
  *до* фиксации, фиксирует, перезагружает и взводит таймер (по умолчанию 90 с, максимум 600 с).
  Нет `uci_confirm` -> файлы атомарно восстанавливаются, подготовленные изменения отменяются,
  службы перезагружаются. Если питание роутера отключилось в течение окна, procd запускает демон
  после сети (S95), и он откатывает изменения при старте, принудительно вызывая `config.change`
  для каждой восстановленной конфигурации.
- **Чужие правки не затрагиваются.** Любой инструмент, который фиксирует изменения, отказывается
  работать, пока у конфигураций, которые он зафиксировал бы, есть незафиксированные изменения из
  другой сессии, и пока ожидает подтверждения неподтверждённое применение.
- **Проверка до перезагрузки.** Пробный запуск прогоняет подготовленную конфигурацию через
  собственный проверяющий механизм службы, где он есть (`fw4 check` для файрвола), и перечисляет
  только те проблемы, которые изменение *добавляет*. Реальное применение отказывает при них, если
  не задано `force=true`; конфигурацию, которая уже была сломана, всё равно можно починить. У
  dnsmasq, dropbear и остальных нет проверки, которая видит подготовленные изменения: о них
  сообщается «не проверено», а не «пройдено».
- **Чтение обратно после записи.** `uci_apply` перечитывает каждую конфигурацию после фиксации и
  до любой перезагрузки; `wg_new_client`, `wg_remove_client` и `pkg_change` потом смотрят на
  таблицу пиров, конфигурацию и `/etc/apk/world`; `service_control` сравнивает итоговое состояние
  с действием. Запись, которую роутер принял, но не сохранил, получает статус `NOT_APPLIED`, а
  откат для `uci_apply` остаётся взведённым. Если обратное чтение выполнить нельзя, пишется «Not
  verified». Позиционные секции (`@rule[3]`) сравнить нельзя, их просто считают.
- **Никакой тихой перезаписи.** `uci_get` заканчивается ревизией конфигурации. Передайте её
  обратно как `expected_revisions`, и применение будет отклонено с `CONFLICT`, если конфигурация
  тем временем изменилась (LuCI, другой клиент).
- **Путь управления охраняется.** Изменение интерфейса LAN или его моста, слушателя SSH, а также
  зоны и правила файрвола, пускающих SSH, отклоняется, если вызов не называет `probe` (пинг шлюза,
  разрешение имени) или не задаёт `force=true`. Проверки запускаются после перезагрузки и
  попадают в результат; окно отката для такого изменения по умолчанию 180 с. Набор правил
  статичен (LAN плюс то, что называет dropbear), поэтому он покрывает типичную раскладку, но не
  любую топологию.
- **История и восстановление.** Подтверждение изменения сохраняет версию конфигурации, бывшую до
  него (последние `history_keep`, по умолчанию 5, на каждую конфигурацию, в
  `/etc/openwrt-mcp/history/`). `uci_get history=list` их показывает, `history=diff:<id>`
  сравнивает одну из них с текущей, а `uci_apply restore=<id>` возвращает её тем же путём:
  снимок, проверки и таймер отката. Записи содержат секреты, как и снимки: `0600`, при показе
  маскируются, входят в резервную копию `sysupgrade`. `option history_keep '0'` отключает историю.
- **Никакого самоповышения.** `uci_apply` и `pkg_config_resolve` отказываются работать с
  конфигурацией политик openwrt-mcp при любом разрешении, так что клиент не может написать себе
  более широкую политику. Политики меняются только через `openwrt-mcp allow` / `revoke` на роутере.
- **`@operator` -- мощный пресет.** `uci_apply` на `*` достаёт до любой конфигурации UCI, включая
  `dropbear`, `rpcd` и `uhttpd`, а `pkg_change` ставит пакеты от root. Выдавайте его на рабочую
  сессию (`2h`), а долгоживущие разрешения ограничивайте узкими областями вроде
  `'dhcp.* wireless.*.disabled'`.
- **Имена проверяются по грамматике UCI**, поэтому секция вроде `lan.ipaddr=x` не может заставить
  uci действовать над другим ключом, чем тот, что одобрила область политики.
- **Нигде нет оболочки.** Каждая команда -- это argv; цели и имена, которые можно прочесть как
  опции (`-f`), отклоняются.
- **Спасательные круги.** `service_control` не остановит и не отключит dropbear, network, rpcd и
  openwrt-mcp. У `sysupgrade` нет действия прошивки -- образ проверяют через `test`, а
  прошивают вручную. `wg_remove_client` не удалит туннель, у которого было рукопожатие за
  последние 3 минуты, или тот, через который приходит сеанс, если не принудить.
- **Учётные данные не попадают в диалог.** `wg_new_client` записывает конфигурацию нового клиента
  (вместе с закрытым ключом) в файл в ОЗУ, доступный только root, рядом с сокетом, и возвращает
  открытый ключ и команду, которую нужно выполнить. `openwrt-mcp wg-show <name>` на роутере
  печатает конфигурацию и QR-код в вашем терминале и удаляет файл; невостребованный файл
  удаляется через 24 часа или при следующей перезагрузке. Только `reveal=true` помещает ключ в
  результат, а значит, в контекст модели и журналы провайдера. Резервная копия `sysupgrade`
  создаётся с правами 0600 до того, как в неё что-либо записано, и хранится только новейшая.
  Журнал аудита записывает аргументы и краткое описание, но никогда не вывод инструментов, и
  скрывает поля, похожие на секреты. Закрытый ключ сервера читается из `wg show dump` и
  отбрасывается.
- **Секреты маскируются в выводе инструментов.** `uci_get`, `uci_apply` (дифф и ошибки),
  `pkg_config_diff`, `pkg_config_resolve`, `uci_confirm`, `uci_rollback`, `system_status` и
  `ubus_call` сохраняют форму строки и заменяют значение секретной опции (`key`, `key1`..`key4`,
  `psk`, `password`, `sae_password`, `passphrase`, `private_key`, `preshared_key`, `token`, `pwd`,
  всё, что содержит `secret`...) на `<redacted>`. Журнал аудита использует то же правило. `exec`,
  `logread` и диагностика не маскируются, а `wg_new_client` исключён намеренно. В секции
  `config server`: `list redact_extra 'vendor_blob'` добавляет имена; `option redact_output '0'`
  отключает маскирование, и это фиксируется в аудите. Замаскированный дифф не показывает, что
  изменилось в секрете.
- **Вывод роутера ненадёжен.** Имена хостов, SSID, строки журнала и ответы DNS выбирают другие
  устройства. В каждом результате удаляются управляющие последовательности терминала,
  управляющие символы, символы bidi и нулевой ширины и некорректный UTF-8, а строки обрезаются
  на 1024 байтах (кроме `exec`, `ubus_call`, `wg_new_client` и инструментов конфигурации).
  `network_clients`, `logread` и `net_diag` начинаются со строки `[untrusted text: ...]`. Это
  снижает вероятность того, что модель подчинится такому тексту, но не устраняет её, поэтому не
  допускайте области записи в сессии, которые его читают.
- **Состояние не выходит в веб.** Каталог состояния, журнал аудита и сокет отклоняются, если
  находятся в `/www`, каталоге `cgi-bin` или `home` uhttpd, даже через символическую ссылку.
- **Модель угроз** описана в [SECURITY.md](SECURITY.md).
- **Выводы оригинала остаются в силе:** ACL rpcd не ограничивают процесс root на локальном сокете
  ubus, поэтому на них не полагаются; собственные apply/rollback rpcd хранят состояние в памяти
  rpcd и tmpfs, поэтому снимок наш и лежит на флеш-памяти.

## Проверено

На GL-MT6000, стоковый OpenWrt 25.12.5, установлен шагами `install.sh` и управлялся из Windows
точно так, как это делает Claude Code (`ssh.exe` с ключом принудительной команды, мост stdio):

- **Установка:** служба procd с перезапуском, ссылки `S95`/`K10`, сокет `0600` в каталоге
  `0700`, HTTP только на `127.0.0.1`, строка принудительной команды в `authorized_keys` dropbear,
  политики `@readonly` + ограниченный по времени `@operator` подхватываются без перезапуска.
- **Чтение на живых данных:** все 23 инструмента перечислены со схемами и инструкциями сервера;
  `system_status`, `network_clients`, `wg_list_clients` (предупреждение о повторяющихся именах),
  `service_list`, `pkg_query upgradable`, `pkg_config_diff` (11 настоящих файлов `.apk-new`, диффы
  на уровне настроек), `firewall_show check`, `net_diag ping` с `br-WAN`, фильтрация `logread`,
  `uci_get`, `sysupgrade list`, `ubus_call`.
- **Запись с откатом** (на временной конфигурации UCI): `uci_apply`, включая `set_list` ->
  автоматический откат по истечении срока, файл восстановлен байт в байт, `pending.json` удалён;
  второе применение отклоняется, пока первое ожидает; `uci_confirm`; `uci_rollback` по запросу;
  `dry_run`.
- **WireGuard:** `wg_new_client` с общим ключом PSK (следующий свободный адрес, пир записан в UCI
  и добавлен в ядро «на лету», предупреждение о конечной точке за CGNAT), показан в списке, затем
  `wg_remove_client` -- `/etc/config/network` вернулся байт в байт, пир в ядре исчез. Передача
  ключа из 1.3.0 (второй прогон, на интерфейсе, включённом на время теста через `uci_apply` и
  затем снова выключенном, с ревизией конфигурации, совпавшей с исходной): в результате не было
  закрытого ключа; конфигурация лежала в файле `0600`, доступном только root, в каталоге `0700`
  под `/var/run`; `openwrt-mcp wg-show`, запущенный в терминале оператора, напечатал
  конфигурацию и QR-код и удалил файл. Чтение обратно из 1.4.0 напечатало `Verified: ...` для
  `uci_apply`, `wg_new_client` и `wg_remove_client`, каждый раз при взведённом откате, после чего
  изменение подтверждалось.
- **Восстановление после сбоя:** демон убит `SIGKILL` при неподтверждённом применении -> procd
  перезапустил его через 6 с, и при старте он откатил изменение.
- **Отказы:** `exec`, `ubus_call session.list`, `uci_apply` вне области (каждый называет строку
  разрешения), любой `uci_apply` по конфигурации политик, HTTP без аутентификации (записано в
  аудит).
- **Безопасность вывода (1.1.0), на той же плате:** `uci_get wireless` и `ubus_call
  network.wireless status` возвращают `<redacted>` для каждого `key` Wi-Fi, а `ssid`,
  `encryption` и похожие имена вроде `wpa_disable_eapol_key_retries` остаются нетронутыми (числа,
  булевы значения и массивы в JSON-ответе тоже). Пробный запуск `uci_apply`, задающий ключ,
  показывает его скрытым и ничего не оставляет подготовленным. `network_clients` и `logread`
  начинаются с маркера ненадёжного текста. Пять неверных кодов `mfa_unlock` от клиента без секрета
  блокируют его на 5 минут (шестой отклоняется с указанием времени повтора); журнал аудита
  записывает четыре записи `ERROR`, затем `DENIED`, и ни один отправленный код в нём не
  появляется. Строка syslog, записанная через `ubus call log write` и содержавшая
  последовательности CSI и OSC, цветовой код, BEL и переопределение bidi (всё это встречается и в
  собственном журнале роутера), вернулась через `logread` только с текстом и табуляцией, а
  слишком длинная строка была обрезана на 1024 байтах с пометкой `[+N bytes]`. Синтаксис `uci
  changes` (`+=`, `-=`, `'\''`, голый `-path` для удаления) снят с роутера и стал тестовой
  фикстурой.
- **Надёжные изменения (1.2.0), на той же плате, через мост stdio демона:** `fw4 check` видит
  изменения, подготовленные в uci (на неверное значение он завершается с кодом 0 и печатает
  строки `[!]`, которые и читает проверка): пробный запуск с заведомо неверным значением зоны
  сообщает о нём как о НОВОЙ проблеме, реальное применение отклоняется, и ничего не остаётся
  подготовленным или сохранённым в снимке. Устаревший `expected_revisions` даёт `CONFLICT`;
  текущий проходит; ревизия конфигурации, которую вызов не меняет, отклоняется. Пробный запуск на
  интерфейсе LAN называет путь управления, а реальное применение без проверки отклоняется,
  ничего не подготовив. `add_list` элемента, который уже есть в `system.ntp.server`,
  пропускается. На временной опции в `luci`: применение с проверками `ping` и `resolve`
  сообщает, что обе в порядке после перезагрузки, и взводит откат; подтверждение оставляет
  запись в истории (каталог `0700`, файлы `0600`); `history=diff` показывает, что добавило
  изменение; `restore` возвращает файл байт в байт с его режимом, запускает свою проверку и
  оставляет собственную запись; применение с неудачной проверкой сообщает `PROBE FAILED` при
  всё ещё взведённом откате, а `uci_rollback` возвращает файл байт в байт. `service_control
  restart` демона сообщает «Settled after» его состояние.
- **Внедрение и учётные данные (1.3.0), на той же плате:** сборка была установлена через
  `install.sh`, и `openwrt-mcp version` сообщил 1.3.0. `connect doctor` с ПК на Windows через его
  настоящий OpenSSH прошёл все семь шагов и перечислил 23 инструмента; с ключом, который роутеру
  неизвестен, он остановился на *key accepted*, а с закрытым портом -- на *ssh reachable*, каждый
  раз с исправлением. `connect --write` для Cursor создал ключ штатным `ssh-keygen` ПК, влил
  запись в JSON-файл, а второй запуск сообщил, что запись не изменилась. `diag` напечатал версию,
  плату, форму политик и строки аудита, где адрес SSH-клиента заменён на `ip-1`, и без аргументов
  аудита; `--detail` добавил замаскированные описания. `sysupgrade backup` создал архив с правами
  `-rw-------` (4,3 МБ, так что `sysupgrade -b` сохраняет режим уже существующего файла), а
  вторая копия удалила первую. Демон занимал около 10 МБ в памяти сразу после перезапуска.
- **Очистка сессий (1.3.0), на той же плате:** после перезапуска демона мост stdio, запущенный на
  новой сборке, сразу завершался, и следующий вызов клиента открывал новую сессию без ошибки;
  мосты, всё ещё работавшие на предыдущей сборке, оставались до следующего запроса их клиента.
  `status` свернул 45 истёкших разрешений в одну строку; `prune` их удалил, записал одну запись
  аудита `prune`, и демон перезагрузился только с действующими разрешениями.
- **Диагностика (1.4.0), на той же плате, клиентом `@readonly`:** `system_status mode=doctor`
  показал одну малозначительную находку -- три файла `.apk-new`, ожидающие слияния, что было
  правдой, и ничего лишнего. `mode=audit` показал правило файрвола, пускающее порт WireGuard из
  WAN (правда, и так задумано), и `uhttpd`, слушающий на всех адресах (правда), с ссылкой на вики
  и следующим вызовом для каждой. `logread mode=summary` свернул чуть более тысячи строк примерно
  в пятьдесят различных сообщений. Базовая линия, сохранённая, а затем сравнённая после
  выполнения периодических заданий, каждый раз засчитывала строку мониторинга как новую, потому
  что менялось поле аптайма; поэтому длительности стали `<dur>`, и после исправления тот же
  цикл не показал ничего нового. `net_diag wifi_survey` дал значения занятости, rx, tx и шума
  для канала каждого радиомодуля с расхождением в пределах пункта от сырого вывода `iwinfo
  survey`, снятого раньше в тот же день; `traffic` три секунды замерял интерфейсы и
  ранжировал источники conntrack по байтам; `usage` перечислил устройства из nlbwmon за текущий
  месячный период; `network_clients` показал столбец `AIR`, доли в котором на каждом радиомодуле
  в сумме давали около 100%.
- **Охват и устойчивость (1.5.0), на той же плате, 25.12.5:** сборка развёрнута шагами установщика. `service_list detail=`
  прочитал tailscale, AdGuard Home и podkop. Предупреждения пробного запуска и запись WireGuard прошли на временном
  интерфейсе, созданном для проверки (не LAN и не настоящий туннель) и удалённом после неё: пир добавлен и удалён по пути
  со взведённым откатом, и откат вернул пир на место. `openwrt-mcp call` и сеанс с `--toolset diag --read-only` отработали
  по SSH с ПК. Прогон на железе нашёл ложный `NOT_APPLIED` после удаления пира, который был не последним (анонимные
  идентификаторы секций UCI позиционные, и чтение обратно смотрело не на ту секцию); это исправлено, а подделка в тестах
  теперь перенумеровывает их так же, как UCI.

Модульные и сквозные тесты (настоящий MCP-клиент через транспорт в памяти и через рукопожатие
моста) работают в любой ОС против поддельного роутера: apply/confirm/rollback/таймаут,
**перезапуск внутри окна**, пробный запуск, отказ при чужих подготовленных правках, операции со

семантика масок областей.

**Пока не проверено на железе** (покрыто только тестами с поддельным роутером): `pkg_change` с

ссылке, настоящее отключение питания (путь восстановления тот же, что проверяет тест с `SIGKILL`) и

настоящими Claude Code, Codex, Claude Desktop, Gemini или VS Code (проверены только слияние

`uci_apply`, `wg_new_client` и `wg_remove_client`; `service_control` и `pkg_change` проверялись

передаче ключа WireGuard проверяются в CI на Linux. Для 1.5.0 дополнительно: всё, что связано с `opkg` (24.10) и `fw3`, выведено из исходников и документации пакетов и ни разу не запускалось на настоящем роутере с 24.10 или 21.02 (задание CI `real-target` запускает инструменты пакетов и uci в контейнерах 24.10 и 25.12, где нет netifd, Wi-Fi и межсетевого экрана); и область `reveal`, проверенная только сопоставлением с политикой.   основа этого проекта. Взято из него: статический демон на Go под procd, постоянные политики
  «запрещено по умолчанию» с масками областей, лимитами частоты и сроком действия, bearer-токены,
  хранимые как дайджесты, окна TOTP, журнал аудита JSONL со скрытием секретов, HTTP только на
  loopback, обрезка ответов ubus и идея «подтверди или откатим» для `uci_apply`. История git
  оригинального проекта сохранена в этом репозитории.
- **[jsebgiraldo/openwrt_ssh_mcp](https://github.com/jsebgiraldo/openwrt_ssh_mcp)** -- внешний
  сервер на Python (SSH на каждый вызов, белый список команд по регулярным выражениям), изучен ради
  идей. Четыре из них взяты и заново реализованы здесь:
  1. проверка образа прошивки перед прошивкой (`sysupgrade -T` -> действие `test` у `sysupgrade`);
  2. сведения о прошивке и плате (часть `system_status`);
  3. управление пакетами (переписано под `apk`: `pkg_query`, `pkg_change`);
  4. ping / traceroute / nslookup (`net_diag`).

  Не взято: инструменты пограничного маршрутизатора OpenThread (привязаны к оборудованию), команды
  `opkg` и `iptables` (в 25.12 их нет), инструмент прошивки (необратим и не восстанавливается
  удалённо) и белый список строк оболочки по регулярным выражениям (вместо него argv + области
  политик).

## Участие и безопасность

Отчёты об ошибках и pull request'ы приветствуются -- см. [CONTRIBUTING.md](CONTRIBUTING.md).
Об уязвимостях сообщайте в частном порядке, как описано в [SECURITY.md](SECURITY.md), а не в
публичном issue. Планируемая работа описана в [ROADMAP.md](ROADMAP.md).

**Сообщение об ошибке:** на роутере выполните `openwrt-mcp diag` и вставьте вывод в issue. Он
печатает версию, плату, состояние демона, форму политик и последние 20 строк аудита (`--audit N`),
причём каждый адрес IPv4, IPv6 и MAC, имя хоста, имя DHCP, SSID, домен и имя пира WireGuard
заменён заполнителем (`ip-1`, `mac-1`, `host-1`, `ssid-1`), который для одного и того же значения
остаётся одинаковым. Аргументы аудита не печатаются никогда, а область, краткое описание и текст
ошибки записи -- только с `--detail`, замаскированные так же. Имена сопоставляются с тем, что сам
роутер называет именами, поэтому прочитайте вывод один раз перед вставкой: имя, которое есть
только в свободном тексте, а не в конфигурации роутера, не распознаётся.
